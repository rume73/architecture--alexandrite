## Анализ системы и определение мест для сбора логов

### Какие логи нужно собирать

Проанализировав C4-диаграмму и описание системы, я выделил следующие источники логов:

**1. Internet Shop (Vue, TypeScript)**

- Действия пользователя: создание заказа, загрузка 3D-модели, работа в редакторе.
- Ошибки фронтенда: сбои JS, ошибки сети, таймауты.

**2. Shop API (Java Spring Boot)**

- Входящие запросы: создание заказа, загрузка файла, получение списка товаров.
- Ошибки API: 4xx, 5xx.
- Взаимодействие с Shop DB и S3.
- Отправка сообщений в RabbitMQ.

**3. CRM API (Java Spring Boot)**

- Получение сообщений из RabbitMQ.
- Создание и обновление заказов в CRM DB.
- Отправка сообщений в RabbitMQ для MES.
- Действия продавцов: подтверждение заказа, изменение статуса.

**4. CRM UI (Vue)**

- Действия продавцов: вход, просмотр заказов, подтверждение.
- Ошибки фронтенда.

**5. MES API (C#)**

- Получение сообщений из RabbitMQ.
- Расчёт стоимости заказа.
- Изменение статусов заказа.
- Взаимодействие с MES DB и S3.
- Отправка сообщений в RabbitMQ для CRM.

**6. MES UI (React)**

- Действия операторов: взятие заказа, изменение статуса.
- Ошибки фронтенда.
- Проблемы с загрузкой дашборда.

**7. RabbitMQ**

- Публикация сообщений.
- Доставка сообщений.
- Ошибки обработки, попадание в DLQ.

**8. Shop DB, CRM DB, MES DB (PostgreSQL)**

- Медленные запросы.
- Ошибки подключения.
- Блокировки.

**9. S3 (3d files storage)**

- Загрузка и скачивание файлов.
- Ошибки доступа.

### Схема сбора логов

На диаграмме нужно отметить (красным или другим цветом) следующие системы как источники логов:

- Internet Shop
- Shop API
- CRM API
- CRM UI
- MES API
- MES UI
- RabbitMQ
- Shop DB, CRM DB, MES DB
- S3

Плюс новый компонент - **ELK Stack** (Elasticsearch + Logstash + Kibana) или **OpenSearch**.

## Список необходимых логов с уровнем INFO

### Internet Shop

- Создание заказа: `order_id`, `customer_id`, `timestamp`, `source`.
- Загрузка 3D-файла: `order_id`, `file_size`, `file_format`.
- Работа в 3D-редакторе: `order_id`, `action`, `duration`.

### Shop API

- Входящий запрос: `trace_id`, `method`, `path`, `status_code`, `duration_ms`, `customer_id`.
- Создание заказа: `order_id`, `customer_id`, `amount`, `source`.
- Отправка в RabbitMQ: `order_id`, `queue_name`, `message_id`.
- Ошибка при сохранении в БД: `order_id`, `error_type`, `error_message`.

### CRM API

- Получение сообщения из RabbitMQ: `order_id`, `queue_name`, `message_id`.
- Создание заказа в CRM: `order_id`, `seller_id`, `status`.
- Изменение статуса: `order_id`, `old_status`, `new_status`, `timestamp`.
- Отправка в RabbitMQ: `order_id`, `queue_name`, `message_id`.

### CRM UI

- Действие продавца: `seller_id`, `action` (подтверждение, просмотр), `order_id`.
- Ошибка фронтенда: `error_type`, `error_message`, `stack_trace`.

### MES API

- Получение сообщения из RabbitMQ: `order_id`, `queue_name`, `message_id`.
- Расчёт стоимости: `order_id`, `duration_ms`, `polygons_count`, `price`.
- Изменение статуса: `order_id`, `old_status`, `new_status`, `operator_id`.
- Отправка в RabbitMQ: `order_id`, `queue_name`, `message_id`.
- Ошибка расчёта: `order_id`, `error_type`, `error_message`.

### MES UI

- Действие оператора: `operator_id`, `action` (взятие заказа, смена статуса), `order_id`.
- Ошибка фронтенда: `error_type`, `error_message`, `stack_trace`.
- Долгая загрузка дашборда: `operator_id`, `duration_ms`, `orders_count`.

### RabbitMQ

- Публикация сообщения: `queue_name`, `exchange_name`, `routing_key`, `message_id`, `trace_id`.
- Доставка сообщения: `queue_name`, `consumer_tag`, `message_id`.
- Ошибка обработки: `queue_name`, `message_id`, `error_type`, `retry_count`.
- Попадание в DLQ: `queue_name`, `message_id`, `reason`.

### БД (Shop DB, CRM DB, MES DB)

- Медленный запрос: `db_name`, `query`, `duration_ms`.
- Ошибка подключения: `db_name`, `error_type`, `error_message`.
- Блокировка: `db_name`, `table`, `lock_type`, `duration_ms`.

### S3

- Загрузка файла: `bucket_name`, `object_key`, `file_size`, `duration_ms`.
- Скачивание файла: `bucket_name`, `object_key`, `duration_ms`.
- Ошибка доступа: `bucket_name`, `object_key`, `error_type`.

### Другие уровни логирования

- **WARN** - нестандартные ситуации: неправильный ввод, повторная попытка, превышение лимита.
- **ERROR** - ошибки: исключения, 5xx, сбои интеграции, ошибки БД.
- **DEBUG** - только в dev и release: детальная отладка, SQL-запросы, значения переменных.
- **TRACE** - только в dev: пошаговое выполнение, вход/выход из методов.
- **FATAL** - отказ сервиса, недоступность БД, критические сбои.

## Мотивация

Сейчас ошибки разбираются со слов клиента: клиенты рассказывают, что пошло не так, а разработчики и поддержка тратят часы на воспроизведение. Логов либо нет, либо они разрознены по серверам. Это замедляет диагностику и увеличивает нагрузку на поддержку.

Логирование даст компании:

- **Быструю диагностику.** Вместо часов поиска - минуты: открыл Kibana, нашёл `order_id`, увидел всю историю.
- **Снижение нагрузки на поддержку.** Типовые проблемы решаются по логам без участия разработчиков.
- **Прозрачность.** Видно, что происходило с заказом в каждый момент времени.
- **Основу для алертинга.** Можно настроить уведомления на ошибки и аномалии.
- **Аудит.** Кто, когда и что делал - для безопасности и разбора инцидентов.

### Технические и бизнес-метрики, на которые повлияет логирование

1. **Среднее время диагностики инцидента (MTTR)** - сократится с часов до минут. Цель: < 30 минут.
2. **Количество обращений в поддержку** - снизится за счёт самостоятельной диагностики. Цель: -30%.
3. **Количество повторных ошибок** - снизится, так как причины будут понятны. Цель: -50%.
4. **Время восстановления после сбоя (MTTR)** - сократится за счёт быстрого поиска причины. Цель: < 1 часа.
5. **Удовлетворённость клиентов (NPS)** - меньше проблем - выше лояльность. Цель: рост на 10–15%.

## Приоритеты: что логировать и трейсить в первую очередь

Команда не сможет единовременно покрыть все системы. Поэтому предлагаю следующий порядок:

### Первая очередь (0–2 месяца)

1. **MES API** - здесь расчёт стоимости и изменение статусов. Именно тут заказы «зависают».
2. **RabbitMQ** - корень проблемы с потерянными сообщениями. Без логов очереди не понять, где теряется заказ.
3. **CRM API** - получение и обработка сообщений, изменение статусов.

### Вторая очередь (2–4 месяца)

4. **Shop API** - создание заказов, загрузка файлов.
5. **MES UI** - проблемы с дашбордом, действия операторов.

### Третья очередь (4–6 месяцев)

6. **CRM UI** - действия продавцов.
7. **Internet Shop** - действия пользователей.
8. **БД и S3** - медленные запросы, ошибки доступа.

**Почему так:** сначала закрываем места, где заказы теряются и зависают (MES API, RabbitMQ, CRM API). Это даёт максимальный эффект для бизнеса. Затем - остальные системы.

## Предлагаемое решение

### Технологии

- **ELK Stack** (Elasticsearch + Logstash + Kibana) или **OpenSearch** - для сбора, хранения, поиска и визуализации логов.
- **Filebeat** - агент для сбора логов с серверов и отправки в Logstash / Elasticsearch.
- **Logstash** - обработка, фильтрация и маршрутизация логов.
- **Elasticsearch** - хранение и поиск логов.
- **Kibana** - визуализация и поиск.
- **OpenTelemetry** - для корреляции логов с трейсами (`trace_id`, `span_id`).

### Компоненты, которые нужно внедрить или доработать

#### Новые компоненты

- **Elasticsearch** - кластер из 3 нод для отказоустойчивости.
- **Logstash** - 2 инстанса для обработки.
- **Kibana** - 1 инстанс.
- **Filebeat** - на каждом EC2-инстансе (Shop API, CRM API, MES API, БД, S3).

#### Доработки

- **Shop API, CRM API, MES API** - настроить структурированное логирование (JSON), добавить `trace_id`, `span_id`, `order_id`.
- **Internet Shop, CRM UI, MES UI** - логирование ошибок фронтенда, отправка в ELK.
- **RabbitMQ** - включить плагин для логирования, отправка в ELK.
- **PostgreSQL** - включить slow query log, отправка в ELK.
- **S3** - логирование доступа через Yandex Cloud Logging.

### Схема (обновлённая C4-диаграмма)

На диаграмме добавляются (красным):

- **Filebeat** - на каждом сервисе.
- **Logstash** - обработка.
- **Elasticsearch** - хранение.
- **Kibana** - визуализация.

**Ссылка на диаграмму:** [C4_logging.drawio](https://github.com/rume73/architecture--alexandrite/blob/alexandrite/Task4/diagrams/С4_logging.drawio)


### Как это работает

1. Сервисы пишут логи в JSON с полями: `timestamp`, `level`, `service`, `trace_id`, `order_id`, `message`.
2. Filebeat собирает логи и отправляет в Logstash.
3. Logstash фильтрует, обогащает и отправляет в Elasticsearch.
4. Kibana визуализирует: дашборды по сервисам, поиск по `order_id`, `trace_id`.
5. При ошибках - алерты в Alertmanager - Telegram / Slack.

## Политика безопасности

### Чувствительные данные

- **Не логировать:** пароли, токены, номера карт, персональные данные (ФИО, адрес, телефон).
- **Маскировать:** `customer_id` - хеш, email - `u***@example.com`.
- **Фильтрация:** Logstash-фильтры удаляют или маскируют PII.

### Доступ к логам

- **Kibana** - только для сотрудников с ролью «Поддержка», «Разработчик», «DevOps».
- **Аутентификация** - через корпоративный SSO (Yandex ID или LDAP).
- **Авторизация** - разные роли видят разные индексы (например, QA - только dev).
- **Аудит доступа** - логирование всех запросов к Kibana.

### Шифрование

- TLS между Filebeat - Logstash - Elasticsearch.
- Шифрование данных в Elasticsearch (at rest).

## Политика хранения

### Индексы

- Отдельный индекс под каждую систему: `shop-api-*`, `crm-api-*`, `mes-api-*`, `rabbitmq-*`, `db-*`, `s3-*`.
- Ежедневная ротация индексов (ILM - Index Lifecycle Management).

### Сроки хранения

- **INFO** - 30 дней.
- **WARN** - 60 дней.
- **ERROR** - 90 дней.
- **FATAL** - 180 дней.
- **Аудит безопасности** - 1 год.

### Размер

- Ожидаемый объём: ~10–50 ГБ в день (зависит от нагрузки).
- Retention: 30–90 дней - ~300 ГБ – 4.5 ТБ.
- Использовать hot-warm-cold архитектуру: hot - 7 дней, warm - 30 дней, cold - 90 дней.

## Мероприятия для превращения системы сбора логов в систему анализа

### Алертинг

- **Alertmanager** (в составе ELK или отдельно) - обработка алертов.
- **Правила:**
  - `ERROR` > 10 в минуту - алерт.
  - `FATAL` - немедленный алерт.
  - DLQ в RabbitMQ > 10 - алерт.
  - Заказ в статусе `SUBMITTED` > 30 минут - алерт.
- **Каналы:** Telegram, Slack, email.

### Поиск аномалий

- **Elasticsearch Machine Learning** - автоматическое обнаружение аномалий.
- **Примеры:**
  - Резкий рост создания заказов (4 - 10 000 за секунду) - возможен DDoS.
  - Резкий рост ошибок 5xx - сбой сервиса.
  - Аномальное время расчёта - деградация.
- **Действия:** автоматический алерт + создание тикета в Jira.

### Дашборды в Kibana

- **Общий дашборд:** количество логов по уровням, топ ошибок, топ сервисов.
- **Дашборд по заказам:** путь заказа, время на каждом этапе, застрявшие заказы.
- **Дашборд по RabbitMQ:** очереди, DLQ, скорость обработки.
- **Дашборд по БД:** медленные запросы, блокировки.
