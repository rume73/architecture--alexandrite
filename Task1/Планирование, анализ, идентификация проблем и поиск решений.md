# Идентификация проблем

## 1. Идентификация проблем
### 1.1 Проблемы производительности

P1. Долгая загрузка первой страницы MES (дашборд заказов). Фильтр по статусам и пагинация не решили проблему. Операторам критически важно видеть самые новые заказы, поскольку от этого зависит их вознаграждение - кто взял заказ, тот и получит оплату. Из-за медленной загрузки операторы теряют время и не успевают брать заказы.

P2. Долгий расчёт стоимости заказа. Расчёт занимает 2-3 минуты, а для сложных детализированных моделей - до 30 минут. Заказ долго висит в статусе SUBMITTED, клиент ждёт, а при росте потока заказов через API нагрузка на расчёт кратно увеличивается.

P3. Единственный инстанс БД (запись + чтение). Все базы данных - Shop DB, CRM DB, MES DB - работают на одном инстансе, который обслуживает и запись, и чтение. Это создаёт риск отказа, ограничивает производительность и приводит к блокировкам при росте нагрузки.

### 1.2 Проблемы интеграции и данных

P4. Заказы «зависают» в промежуточных статусах. Клиенты жалуются, что заказы не приходят месяцами, хотя обещано три недели. Проблема не на стороне производства - мощности позволяют выдержать двукратный рост. Значит, заказы теряются или застревают при передаче между системами через RabbitMQ.

P5. Нет гарантий доставки и обработки сообщений. В RabbitMQ отсутствуют DLQ, ретраи и идемпотентность консьюмеров. Это приводит к потере или дублированию сообщений, что напрямую влияет на зависание заказов в статусах.

P6. Данные о заказах дублируются в Shop DB, CRM DB, MES DB. Каждая система хранит свою версию заказа. Это приводит к рассинхронизации, сложности отладки и путанице в статусах.

### 1.3 Проблемы процессов и инфраструктуры

P7. Ручной деплой в release и prod. Версии деплоятся вручную, что замедляет выпуск исправлений и повышает риск человеческих ошибок.

P8. Ручное E2E-тестирование и блокировка релизов. QA-инженер прогоняет E2E-сценарии вручную. При обнаружении багов уровня high или highest версия не деплоится на продакшн до их починки. Это часто приводит к задержкам релиза, которые в последнее время растут.

P9. Нет полноценного мониторинга и алертинга. Проблемы обнаруживаются постфактум, когда клиенты уже жалуются. Нет данных о том, где именно теряются заказы и что тормозит.

### 1.4 Потенциальные проблемы

P10. При дальнейшем росте нагрузки единственный инстанс БД станет узким местом. Рост линейный (+100 заказов в месяц), плюс открытие API для внешних продавцов. Без репликации БД деградация неизбежна.

P11. RabbitMQ без кластеризации - единая точка отказа. При падении очереди встанет вся интеграция между CRM и MES, а значит, и обработка заказов.

P12. Отсутствие rate limiting на публичном API. Внешние продавцы могут перегрузить систему, особенно если один из них отправит большой поток заказов. Это риск DDoS и неконтролируемой нагрузки.


## 2. Инициативы по устранению проблем

### 2.1 Список инициатив

I1. Настройка RabbitMQ: DLQ, ретраи, идемпотентность консьюмеров, кластеризация. Закрывает P4, P5, P11. Быстро, дёшево, снимает корневую причину зависаний заказов.

I2. Внедрение наблюдаемости: OpenTelemetry + Jaeger для трейсинга, ELK для логов, Prometheus + Grafana для метрик и алертинга. Закрывает P9. Без наблюдаемости нельзя понять, где именно теряются заказы и что тормозит. Трейсинг покажет путь заказа через Shop API → RabbitMQ → CRM API → MES API, а логи - причины зависаний.

I3. Оптимизация дашборда MES: кэширование через Redis (паттерн Cache-Aside) + материализованные представления + read-инстанс. Закрывает P1, P3. Прямая боль операторов, влияет на их доход. Cache-Aside для списка новых заказов, инвалидация при смене статуса.

I4. Асинхронный расчёт стоимости: вынос в воркер с очередью + паттерн Backpressure для защиты от перегрузки. Закрывает P2. Снимает нагрузку с MES API, ускоряет обработку. Backpressure ограничит приток заказов при пиковой нагрузке.

I5. Репликация БД: read replicas для Shop DB, CRM DB, MES DB + паттерн Read-Through для чтения. Закрывает P3, P10. Снимает нагрузку с основных инстансов, снижает риск отказа.

I6. Автоматизация CI/CD: авто-деплой в release, blue-green в prod. Закрывает P7. Ускоряет релизы, снижает риск ошибок.

I7. Найм: автоматизатор тестирования, второй DevOps. Закрывает P8. Нужен для масштабирования процессов и автоматизации.

I8. Rate limiting и версионирование публичного API + Circuit Breaker для внешних вызовов. Закрывает P12. Circuit Breaker защитит MES API от каскадных отказов при проблемах у внешних продавцов. Rate limiting - от перегрузки.

I9. HTTP-кэширование для статики и ответов Shop API.

### 2.2 Приоритизация и ход рассуждений

Высокий приоритет (0–2 месяца):

I1. Наблюдаемость (OpenTelemetry, Jaeger, ELK, Prometheus, Grafana) - фундамент для определения корневых проблем.
I2. RabbitMQ - корень проблемы с зависшими заказами.
I3. Дашборд MES (Redis + Cache-Aside) - прямая боль операторов.

Средний приоритет (2–4 месяца):

I4. Асинхронный расчёт + Backpressure - снимает нагрузку с MES API.
I5. Репликация БД + Read-Through - снижает нагрузку и риск отказа.
I6. CI/CD - ускоряет релизы.
I7. Найм - нужен для масштабирования.
Низкий приоритет (4–6 месяцев):

I8. Rate limiting + Circuit Breaker + версионирование API.
I9. HTTP-кэширование для Shop API и статики.

### 2.3 Целевая архитектура через полгода

Приложения. MES API разделён на MES Order Service и MES Calculation Service (воркеры + очередь + Backpressure). MES UI работает с Redis-кэшем (Cache-Aside). CRM API и Shop API - с репликами БД и Read-Through.

Данные. PostgreSQL с read replicas. RabbitMQ кластеризован, с DLQ, ретраями и идемпотентными консьюмерами. Redis для кэша дашборда MES.

Наблюдаемость. OpenTelemetry для инструментирования, Jaeger для трейсинга, ELK для логов, Prometheus + Grafana для метрик и алертов.

Инфраструктура. Auto-scaling группы. CI/CD: авто-деплой в release, blue-green в prod. Rate limiting и Circuit Breaker на API Gateway.

Процессы. E2E-тесты автоматизированы. В команде: 2 DevOps, 2 QA (один - автоматизатор), 3 бэкенд-разработчика.

### 2.4 Три инициативы на ближайшие полгода

1. I1. Наблюдаемость: OpenTelemetry + Jaeger + ELK + Grafana.
Без трейсинга и логов не понять, где теряются заказы. Jaeger покажет путь заказа, ELK - ошибки, Grafana — метрики. Внедряется за 1–2 недели.

2. I2. RabbitMQ: DLQ, ретраи, идемпотентность, кластеризация.
Корень проблемы с зависшими заказами. После внедрения мониторинга сразу увидим эффект. Внедряется за 1–2 недели.

3. I3. Дашборд MES: Redis (Cache-Aside) + read-инстанс.
Прямая боль операторов, влияет на их доход. Кэш новых заказов с инвалидацией при смене статуса даст мгновенную загрузку. Решается за 2–4 недели.
