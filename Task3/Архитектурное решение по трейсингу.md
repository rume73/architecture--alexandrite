## Анализ системы и определение мест для трейсинга

### Где заказ может «сломаться» или зависнуть

Проанализировав C4-диаграмму и описание системы, я выделил следующие точки:

**1. Internet Shop - Shop API**

Заказ создаётся в браузере, отправляется в Shop API. Если запрос теряется или Shop API недоступен - заказ не создаётся, пользователь не понимает, что произошло.

**2. Shop API - Shop DB**

Заказ сохраняется в БД. Если запись не проходит (блокировка, таймаут), заказ теряется.

**3. Shop API - S3 (3d files storage)**

Загрузка 3D-файла. Если файл не загрузился или загрузился частично - расчёт стоимости невозможен.

**4. Shop API - RabbitMQ**

Сообщение о новом заказе отправляется в очередь. Если сообщение не доставлено - CRM не узнает о заказе.

**5. RabbitMQ - CRM API**

CRM API получает сообщение и создаёт заказ в CRM. Если консьюмер падает или сообщение уходит в DLQ - заказ зависает.

**6. CRM API - CRM DB**

Сохранение заказа в CRM. Если запись не проходит - заказ теряется.

**7. CRM API - RabbitMQ**

Сообщение о подтверждении заказа (`MANUFACTURING_APPROVED`) отправляется в MES. Если сообщение не доставлено - MES не начнёт производство.

**8. RabbitMQ - MES API**

MES API получает сообщение. Если консьюмер падает - заказ зависает в статусе `MANUFACTURING_APPROVED`.

**9. MES API - S3 (3d files storage)**

MES API забирает 3D-файл для расчёта. Если файл недоступен - расчёт не проходит.

**10. MES API - MES DB**

Сохранение статуса и результатов расчёта. Если запись не проходит - статус не обновляется.

**11. MES API - RabbitMQ**

Сообщение об изменении статуса (`MANUFACTURING_STARTED`, `MANUFACTURING_COMPLETED`, `PACKAGING`, `SHIPPED`) отправляется в CRM. Если сообщение не доставлено - CRM не узнает о прогрессе.

**12. RabbitMQ - CRM API**

CRM API получает сообщение об изменении статуса. Если консьюмер падает - статус в CRM не обновляется, заказ «зависает» для продавца.

**13. MES API - Operator (MES UI)**

Оператор видит список заказов. Если дашборд тормозит - оператор не берёт заказ, заказ зависает.

**14. CRM API - Seller (CRM UI)**

Продавец видит статус заказа. Если статус не обновляется - продавец не может ответить клиенту.

### Системы, которые следует покрыть трейсингом

**Обязательно:**

- Internet Shop (фронтенд)
- Shop API
- CRM API
- MES API
- RabbitMQ (через консьюмеры и продюсеры)
- Shop DB, CRM DB, MES DB (через вызовы)
- S3 (через вызовы)

**Дополнительно:**

- CRM UI
- MES UI
- Отслеживание пользовательских сессий

## Список данных, которые должны попадать в трейсинг

### Контекст операции (OpenTelemetry)

- `trace_id` - идентификатор всего заказа.
- `span_id` - идентификатор каждого подзапроса.
- `parent_span_id` - идентификатор родительского span.
- `service_name` - название сервиса (`shop-api`, `crm-api`, `mes-api`).
- `environment` - окружение (`dev`, `release`, `prod`).
- `node_name` - имя ноды / инстанса.

### Атрибуты заказа

- `order_id` - идентификатор заказа.
- `order_status` - текущий статус.
- `order_source` - источник (`B2C`, `API`).
- `customer_id` - идентификатор клиента.
- `api_user_id` - идентификатор внешнего продавца (если есть).

### HTTP/gRPC

- `http_method`, `http_path`, `http_status_code`.
- `duration_ms` - время выполнения.
- `request_size`, `response_size`.

### RabbitMQ

- `queue_name`, `exchange_name`, `routing_key`.
- `message_id`, `correlation_id`.
- `retry_count`, `dlq_reason`.

### БД

- `db_system`, `db_name`, `db_operation` (`SELECT`, `INSERT`, `UPDATE`).
- `db_statement` (без чувствительных данных).
- `db_duration_ms`.

### S3

- `bucket_name`, `object_key`, `operation` (`GET`, `PUT`).
- `file_size`.

### Ошибки

- `error_type`, `error_message`, `stack_trace`.
- `error_code`.

## Мотивация

Сейчас команда не может ответить на простой вопрос: **где именно завис заказ?** Клиенты жалуются, что заказы не приходят месяцами, но нет данных, чтобы понять, на каком этапе теряется заказ - в Shop API, RabbitMQ, CRM API или MES API. Логи есть не везде, а их объём и стоимость хранения растут.

Трейсинг даст компании:

- **Прозрачность.** Видно весь путь заказа от создания до закрытия - по всем сервисам и очередям.
- **Быструю диагностику.** Вместо часов поиска - минуты: открыл Jaeger, нашёл `trace_id`, увидел, где оборвалась цепочка.
- **Снижение оттока клиентов.** Быстрое решение проблем - меньше жалоб - меньше потерянных контрактов.
- **Обоснование решений.** Данные о времени на каждом этапе - понятно, что оптимизировать.
- **Контроль SLA для API-партнёров.** Можно показать внешним продавцам, что система работает стабильно.

### Технические и бизнес-метрики, на которые повлияет трейсинг

1. **Среднее время обработки заказа (Order Processing Time)** - трейсинг покажет, на каком этапе заказ тормозит. Цель: сократить с 3 недель до 2.
2. **Количество заказов, застрявших в статусе (Stuck Orders)** - трейсинг покажет, где именно застревают заказы. Цель: снизить на 80%.
3. **Среднее время диагностики инцидента (MTTR)** - с трейсингом сократится с часов до минут. Цель: < 30 минут.
4. **Количество потерянных сообщений в RabbitMQ (Lost Messages)** - трейсинг покажет, какие сообщения не дошли. Цель: 0.
5. **Удовлетворённость клиентов (NPS / Retention)** - меньше проблем - выше лояльность. Цель: рост на 10–15%.

## Предлагаемое решение

### Технологии

- **OpenTelemetry (OTel)** - стандарт для сбора телеметрии. SDK встраивается в Shop API, CRM API, MES API, Internet Shop, CRM UI, MES UI.
- **Jaeger** - инструмент для визуализации трейсов. Разворачивается в Yandex Cloud как отдельный сервис.
- **OpenTelemetry Collector** - принимает данные от SDK, обрабатывает и экспортирует в Jaeger.
- **Context Propagation** - передача `trace_id` и `span_id` через HTTP-заголовки (`traceparent`) и заголовки RabbitMQ (`x-trace-id`, `x-span-id`).

### Компоненты, которые нужно внедрить или доработать

#### Новые компоненты

- **Jaeger** (all-in-one или распределённый: collector, query, storage).
- **OpenTelemetry Collector** - для приёма и маршрутизации телеметрии.
- **Хранилище для трейсов** - Elasticsearch или Cassandra (в зависимости от нагрузки).

#### Доработки

- **Shop API, CRM API, MES API** - встроить OTel SDK, настроить экспорт в Collector.
- **Internet Shop, CRM UI, MES UI** - встроить OTel SDK для браузера (OTel JS).
- **RabbitMQ** - настроить propagation контекста через заголовки сообщений. Продюсеры добавляют `traceparent` в заголовки, консьюмеры извлекают.
- **PostgreSQL** - настроить OTel-инструментацию для запросов (опционально, через библиотеки).
- **S3** - инструментировать вызовы через OTel SDK.

### Схема

На диаграмме добавляются:

- **Jaeger** (красный) - сервис для сбора и визуализации трейсов.
- **OpenTelemetry Collector** (красный) - приёмник телеметрии.
- **Связи** (красные) от Shop API, CRM API, MES API, RabbitMQ, Internet Shop, CRM UI, MES UI к OTel Collector - Jaeger.

**Ссылка на диаграмму:** [C4_tracing.drawio](https://github.com/rume73/architecture--alexandrite/blob/alexandrite/Task3/diagrams/С4_tracing.drawio)

## Компромиссы

### 1. Проприетарные системы

MES куплен вместе с исходным кодом, но если бы он был закрытым - встроить OTel SDK было бы сложно или дорого. Пришлось бы использовать внешние инструменты (eBPF, service mesh) или дорабатывать систему за деньги вендора.

### 2. Стоимость хранения

Трейсы - объёмные данные. При росте нагрузки (100+ заказов в месяц) хранилище будет расти. Нужно настроить sampling (например, 10% успешных запросов, 100% ошибок) и retention policy (например, 30 дней).

### 3. Overhead на производительность

OTel SDK добавляет небольшой overhead (1–5%) на каждый запрос. При высокой нагрузке это может быть заметно. Нужно тестировать и при необходимости использовать асинхронный экспорт.

### 4. Legacy-код

Если в коде нет структурированных вызовов (например, прямые SQL-запросы), инструментировать их сложнее. Придётся добавлять spans вручную.

### 5. RabbitMQ propagation

Нужно доработать всех продюсеров и консьюмеров, чтобы они передавали и извлекали `traceparent`. Это требует изменений в коде на C# и Java.

### 6. Обучение команды

Нужно время, чтобы команда научилась работать с Jaeger и OTel. Провести воркшоп.

## Безопасность

### Внутри компании

- Доступ к Jaeger UI - только для сотрудников с актуальной учётной записью и ролью «Поддержка» или «Разработчик».
- Аутентификация через корпоративный SSO (Yandex ID или LDAP).
- Авторизация: разные роли видят разные сервисы (например, QA видит только тестовые окружения).
- Логирование доступа к Jaeger (кто, когда, какой трейс смотрел).

### Снаружи

- Jaeger не доступен из интернета. Только через VPN или внутреннюю сеть.
- OTel Collector принимает данные только от авторизованных сервисов (mTLS или API-ключи).
- Данные трейсов не содержат PII (персональных данных). Нужно настроить фильтрацию: не логировать `customer_id` в открытом виде, использовать хеши.
- Шифрование трафика между сервисами и Collector (TLS).
