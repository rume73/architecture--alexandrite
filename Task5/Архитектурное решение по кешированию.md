## Анализ системы

**1. Низкая скорость работы MES UI (дашборд операторов).**

Операторы жалуются, что первая страница MES долго грузится. Фильтр по статусам и пагинация не помогли. Операторам важно видеть **самые новые заказы**, потому что от этого зависит их вознаграждение - кто взял заказ, тот и получит оплату.

**2. Низкая скорость выполнения заказа (расчёт стоимости).**

Расчёт стоимости в MES API занимает 2–3 минуты, а для сложных моделей - до 30 минут. Это не кеширование в чистом виде, но при повторных запросах одну и ту же модель можно не пересчитывать.

### Что имеет смысл кешировать

- **Список заказов на дашборде MES** - самая горячая точка. Операторы постоянно обновляют страницу, чтобы увидеть новые заказы.
- **Результаты расчёта стоимости** - если одна и та же 3D-модель отправляется на расчёт повторно, результат можно взять из кеша.
- **Справочные данные** - список статусов, список операторов, настройки - меняются редко, можно кешировать надолго.
- **Данные о заказах в CRM** - продавцы часто смотрят одни и те же заказы.

**Что кешировать не стоит:**

- Данные, которые меняются каждую секунду (например, счётчик онлайна).
- Персональные данные без необходимости (из соображений безопасности).
- Данные, которые редко запрашиваются.

## Мотивация

Сейчас MES UI тормозит: каждый раз при загрузке дашборда MES API идёт в MES DB и делает тяжёлый запрос по всем заказам. При росте нагрузки (+100 заказов в месяц) это становится критично. Операторы теряют время, не видят новые заказы, страдает производство.

Кеширование даст компании:

- **Скорость.** Дашборд MES будет грузиться мгновенно из кеша, а не из БД.
- **Снижение нагрузки на БД.** Тяжёлые запросы уйдут в Redis, MES DB разгрузится.
- **Рост производительности операторов.** Они быстрее видят новые заказы - быстрее берут их в работу - растёт вознаграждение.
- **Экономию.** Меньше нагрузки на БД - можно отложить масштабирование.
- **Ускорение расчёта.** Повторные расчёты одной модели берутся из кеша.

**Элементы системы, которые планирую включить в кеширование:**

- Список заказов на дашборде MES (Redis).
- Результаты расчёта стоимости (Redis).
- Справочные данные (Redis, долгий TTL).
- Список заказов в CRM (Redis, короткий TTL).

## Предлагаемое решение

### Какое кеширование внедрять

**Серверное кеширование через Redis.** Клиентское (в браузере) не подойдёт, потому что:

- Данные о заказах общие для всех операторов - кеш должен быть централизованным.
- Нужна инвалидация при изменении статуса - браузер не узнает об этом.
- Нужен контроль TTL и стратегии - это проще делать на сервере.

**Где именно:**

- **MES API** - кеш списка заказов и результатов расчёта.
- **CRM API** - кеш списка заказов и справочных данных.

**Технология:** **Redis** - быстрый, поддерживает TTL, структуры данных (Sorted Set для сортировки заказов по времени), Pub/Sub для инвалидации.

### Паттерн кеширования

**Cache-Aside (Lazy Loading).**

**Почему Cache-Aside:**

- Приложение сначала идёт в кеш. Если данных нет - идёт в БД, кладёт в кеш, возвращает.
- При изменении данных - приложение обновляет БД и инвалидирует кеш.
- Гибко: можно кешировать только то, что нужно.
- Не требует сложной инфраструктуры.

**Почему не Write-Through:**

- Write-Through пишет в кеш и БД одновременно при каждой записи. Для нашего случая это избыточно: заказы меняются не так часто, как читаются.
- Усложняет логику записи, требует синхронности.

**Почему не Refresh-Ahead:**

- Refresh-Ahead обновляет кеш заранее, до истечения TTL. Это сложнее и требует предсказания, какие данные понадобятся.
- Для нашего случая достаточно Cache-Aside: данные читаются часто, но не настолько, чтобы предсказывать.

**Что кешируем:**

- **Список заказов на дашборде MES** - Sorted Set по времени создания. Ключ: `mes:orders:new`. TTL: 30 секунд.
- **Список заказов по статусу** - ключ: `mes:orders:status:{status}`. TTL: 30 секунд.
- **Результат расчёта стоимости** - ключ: `mes:price:{hash_of_3d_model}`. TTL: 24 часа.
- **Справочные данные** - ключ: `mes:ref:{type}`. TTL: 1 час.

### Стратегия инвалидации кеша

**Программная инвалидация по ключу + временная (TTL).**

**Как работает:**

- При изменении статуса заказа (например, `MANUFACTURING_STARTED`) MES API:
  1. Обновляет заказ в MES DB.
  2. Инвалидирует ключи: `mes:orders:new`, `mes:orders:status:{old_status}`, `mes:orders:status:{new_status}`.
  3. Публикует событие в Redis Pub/Sub, чтобы другие инстансы MES API тоже инвалидировали кеш.
- Параллельно работает TTL: даже если инвалидация не сработала, данные устареют через 30 секунд.

**Почему программная + TTL:**

- Программная инвалидация даёт мгновенную актуальность - оператор сразу видит новый заказ.
- TTL - страховка на случай сбоя инвалидации.
- Вместе они дают и скорость, и надёжность.

**Почему не только временная:**

- Оператор может не увидеть новый заказ до 30 секунд - это критично для вознаграждения.

**Почему не только программная:**

- Если инвалидация не сработает (сбой, потеря сообщения), данные останутся устаревшими навсегда.

**Почему не по ключу через БД-триггеры:**

- Сложно поддерживать, требует доступа к БД, не масштабируется.

### Сравнительный анализ стратегий инвалидации

| Критерий | Программная + TTL | Только TTL | Только программная |
|---|---|---|---|
| Актуальность | Мгновенная актуальность + страховка | Данные могут быть устаревшими до 30 секунд | Мгновенная актуальность, но риск «залипшего» кеша |
| Сложность | Требует кода инвалидации | Не требует кода | Требует кода |
| Применение | Подходит для горячих данных | Подходит для справочников | Подходит, если инвалидация надёжна |

**Выбор: программная + TTL.**

**Сущности, участвующие в кешировании:**

- MES UI (React)
- MES API (C#)
- Redis (кеш)
- MES DB (PostgreSQL)
- RabbitMQ (для событий статусов)
