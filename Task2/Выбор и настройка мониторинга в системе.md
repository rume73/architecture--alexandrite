## Мотивация

Сайт «Александрит» подключён к Яндекс Метрике, но с открытием API для внешних продавцов этих данных уже недостаточно. Яндекс Метрика видит только B2C-пользователей и не показывает, что происходит внутри системы: сколько заказов теряется в RabbitMQ, как долго рассчитывается стоимость, какие сервисы деградируют под нагрузкой.

Бизнес теряет крупные контракты и получает жалобы от клиентов, но не имеет данных, чтобы понять причину. Мониторинг даст компании:

- **Прозрачность.** Видно, на каком этапе заказ «зависает» — в Shop API, RabbitMQ, CRM API или MES API.
- **Раннее обнаружение проблем.** Алерты срабатывают до того, как клиент пожалуется, а не после.
- **Обоснование решений.** Вместо гипотез — данные: где узкое место, что масштабировать, что оптимизировать.
- **Контроль SLA для API-партнёров.** Можно показать внешним продавцам, что система работает стабильно.
- **Экономию.** Мониторинг дешевле, чем потеря контрактов и репутации.

---

## Выбор подхода к мониторингу

Для разных частей системы использую разные подходы:

### RED

Для всех API-сервисов, которые управляются запросами:

- Shop API
- CRM API
- MES API
- RabbitMQ (как очередь запросов)

RED подходит, потому что эти сервисы обрабатывают запросы, и для бизнеса важны частота, ошибки и длительность.

### USE

Для инфраструктурных ресурсов:

- CPU, память, диск на EC2-инстансах
- PostgreSQL (Shop DB, CRM DB, MES DB)
- S3-хранилище

USE подходит для ресурсов, производительность которых падает при интенсивном использовании.

### Четыре золотых сигнала

Для общего контроля системы в целом:

- Задержка
- Трафик
- Ошибки
- Насыщенность

Это дополняет RED и USE, давая целостную картину.

## Метрики для отслеживания

### 1. RabbitMQ

> Критично — корень проблемы с зависшими заказами.

#### Number of dead-letter-exchange letters in RabbitMQ

- **Зачем:** показывает, сколько сообщений не удалось обработать и они ушли в DLQ. Рост этой метрики — прямой сигнал, что заказы теряются.
- **Ярлыки:** `queue_name`, `exchange_name`, `routing_key`.

#### Number of messages in flight in RabbitMQ

- **Зачем:** показывает, сколько сообщений сейчас в обработке. Рост — сигнал, что консьюмеры не справляются.
- **Ярлыки:** `queue_name`, `consumer_tag`.

#### Number of messages ready in RabbitMQ

- **Зачем:** показывает очередь необработанных сообщений. Рост — сигнал, что заказы копятся.
- **Ярлыки:** `queue_name`.

### 2. API-сервисы

Shop API, CRM API, MES API.

#### Number of requests (RPS) for Shop API / CRM API / MES API

- **Зачем:** базовая метрика нагрузки. Позволяет понять пиковые часы и планировать ресурсы.
- **Ярлыки:** `endpoint`, `method`, `status_code`.

#### Number of requests (RPS) per user for Shop API / CRM API / MES API

- **Зачем:** показывает, не злоупотребляет ли один пользователь API. Важно для rate limiting.
- **Ярлыки:** `user_id`, `api_key`, `endpoint`.

#### Response time (latency) for Shop API / CRM API / MES API

- **Зачем:** ключевая метрика для RED. Показывает, как быстро сервис отвечает. Рост — сигнал деградации.
- **Ярлыки:** `endpoint`, `method`, `status_code`, `quantile` (p50, p95, p99).

#### Number of HTTP 200 for Shop API / CRM API / MES API

- **Зачем:** показывает успешные запросы. Базовая линия для сравнения с ошибками.
- **Ярлыки:** `endpoint`, `method`.

#### Number of HTTP 500 for Shop API / CRM API / MES API

- **Зачем:** показывает ошибки сервера. Рост — сигнал проблем.
- **Ярлыки:** `endpoint`, `method`, `error_type`.

#### Number of simultaneous sessions for Shop API / CRM API / MES API

- **Зачем:** показывает, сколько пользователей одновременно работают. Помогает планировать ресурсы.
- **Ярлыки:** `service_name`.

#### Kb transferred (received) for Shop API / CRM API / MES API

- **Зачем:** показывает входящий трафик. Важно для понимания нагрузки на сеть.
- **Ярлыки:** `endpoint`, `method`.

#### Kb provided (sent) for Shop API / CRM API / MES API

- **Зачем:** показывает исходящий трафик. Важно для стоимости облака и пропускной способности.
- **Ярлыки:** `endpoint`, `method`.

### 3. Инфраструктура (EC2-инстансы)

#### CPU % for Shop API / CRM API / MES API

- **Зачем:** показывает утилизацию процессора. Рост до 80–90% — сигнал масштабироваться.
- **Ярлыки:** `instance_id`, `service_name`.

#### Memory Utilisation for Shop API / CRM API / MES API

- **Зачем:** показывает потребление памяти. Утечки или рост — сигнал проблем.
- **Ярлыки:** `instance_id`, `service_name`.

### 4. Базы данных

#### Memory Utilisation for Shop DB instance / MES DB instance

- **Зачем:** показывает потребление памяти БД. Рост — сигнал, что нужно масштабировать.
- **Ярлыки:** `db_instance_id`, `db_name`.

#### Number of connections for Shop DB instance / MES DB instance

- **Зачем:** показывает количество подключений. Близко к лимиту — сигнал проблем.
- **Ярлыки:** `db_instance_id`, `db_name`.

#### Size of Shop DB instance / MES DB instance

- **Зачем:** показывает рост БД. Помогает планировать место.
- **Ярлыки:** `db_instance_id`, `db_name`.

### 5. S3-хранилище

#### Size of S3 storage

- **Зачем:** показывает объём 3D-файлов. Рост — сигнал планировать место и стоимость.
- **Ярлыки:** `bucket_name`.

### 6. Бизнес-метрики

#### Number of orders by status

- **Зачем:** показывает, сколько заказов в каждом статусе. Заказы, застрявшие в `SUBMITTED` или `PRICE_CALCULATED`, — прямой сигнал проблемы.
- **Ярлыки:** `status`, `source` (B2C / API).

#### Order processing time

- **Зачем:** показывает, сколько времени заказ идёт от создания до закрытия. Рост — сигнал для бизнеса.
- **Ярлыки:** `status`, `source`.

## План действий

1. **Развернуть time-series базу.** Использовать Prometheus для сбора метрик или InfluxDB / ClickHouse для хранения.
2. **Настроить сбор метрик.** Подключить OpenTelemetry SDK к Shop API, CRM API, MES API. Настроить экспортёры для RabbitMQ, PostgreSQL, EC2.
3. **Развернуть Grafana.** Создать дашборды по RED для каждого API, USE для инфраструктуры, отдельный дашборд для RabbitMQ и бизнес-метрик.
4. **Настроить алертинг.** Использовать Alertmanager. Настроить уведомления в Telegram / Slack / email.
5. **Настроить трейсинг.** Развернуть Jaeger, подключить OpenTelemetry для трассировки заказов через все сервисы.
6. **Настроить логирование.** Развернуть ELK (Elasticsearch + Logstash + Kibana) для централизованного сбора логов.
7. **Определить пороги насыщенности.** Для каждой метрики задать warning и critical уровни.
8. **Обучить команду.** Провести воркшоп по работе с Grafana, Jaeger, Kibana.
